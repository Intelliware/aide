# generate-ai-rules — Inputs & Outputs

## Inputs

| Input | Source / Path | Required | Used by step | Notes |
|---|---|---|---|---|
| `project.toml` | `{project-root}/project.toml` | Yes | 01–04 | `[[project.repos]]` drives per-repo loop in Step 01. |
| RE Part A — package & build files | `<KB>/source-docs/<repo>/part-a/**` (resolved package.json, requirements.txt, *.csproj, build configs) | Yes | 01 | Source of exact versions and build/test commands. |
| RE Part A — observed patterns sections | `<KB>/source-docs/<repo>/part-a/**/patterns.md` | No | 01 | Auto-detect lint config, mocking style, error-handling patterns. |
| `30-constraints-and-compliance.md` § 5 | `<KB>/shared/solution-context/` | No (warns if missing) | 02, 03 | Architectural must-nots feed § 8 of the output. |
| Component `verification_signal` distribution | `<KB>/components/<repo>/<id>.md` frontmatter | No | 02 | Distribution informs which test types to require. |
| Existing `project-context.md` | `<KB>/shared/ai-rules/project-context.md` | No | 01 | Step 01 detects and asks: refresh / replace. |
| Elicitation pattern | `references/elicitation-patterns/coding-rules.md` (NEW; see Stage 3) | Yes (interactive) | 02 | Drives the elicitation script. |
| `--non-interactive` flag | CLI / invocation | No | 02 | Skips elicitation; emits TODO stubs. |
| `--force-overrides` flag | CLI / invocation | No | 03 | Forces per-repo override generation regardless of divergence threshold. |

## Outputs

| Output | Path | Generated by step | Notes |
|---|---|---|---|
| Canonical AI rules doc | `<KB>/shared/ai-rules/project-context.md` | 03 | Always emitted; target < 300 lines. |
| Per-repo overrides | `<KB>/shared/ai-rules/per-repo/<repo-slug>.md` | 03 | Only when Step 03 divergence check fires. |
| Frontmatter on canonical doc | (inline) | 03 | See template below. |

## Canonical doc frontmatter

```yaml
---
ai_rules_id: project-context
description: >-
  Use when an AI agent is about to write or modify code in any repo of
  this project; this document is the contract for tech stack, language
  conventions, testing discipline, and architectural must-nots.
triggers:
  - coding rules
  - ai rules
  - project context
  - tech stack
  - language conventions
  - testing rules
  - branch naming
  - commit conventions
last_generated: <ISO-8601 date>
last_generated_by: <user_id>
covers_repos:
  - <repo-code-1>
  - <repo-code-2>
divergence_overrides:
  - <repo-slug-1>   # only when Step 03 emitted an override file
---
```

## Validation gate (Step 03 output)

| Check | Acceptance criterion |
|---|---|
| Required sections | All nine sections § 1–9 present. |
| Auto-fill correctness | Every version in § 1 matches the lock-file or build-config evidence; the skill prints a diff report. |
| Frontmatter | `description` starts with `Use when `; `covers_repos` matches `[[project.repos]]` codes. |
| Imperative form | Each rule in § 2–7 is phrased as a concrete imperative (`Always …` / `Never …`), not advice. Step 03 spot-checks. |
| Length | `project-context.md` ≤ 300 lines (warn) / ≤ 500 lines (fail). |
| Cross-links | § 9 references the operations and solution-context outputs by path. |
| Override policy | If per-repo override files exist, each carries a one-line "Why this override exists" header. |
| Constraint feed | § 8 contains every entry from `30-constraints-and-compliance.md` § 5 OR explicitly states "no architectural prohibitions captured" with a link forward. |
