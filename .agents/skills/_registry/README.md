# Skill Registry

Two artifacts power skill discovery and routing:

## `skills.csv` (generated)

Auto-generated by `scripts/build-registry.py`. Walks `.agents/skills/**/SKILL.md`, parses YAML frontmatter, emits one CSV row per skill with columns: `canonical_id, name, description, stage, package, path, origin`.

The `origin` column is `core` for framework skills. Add-on skills (from repos passed via `--extra-skill-root` or `framework.toml [registry].extra_skill_roots`) carry their add-on's name and sort after all core rows. See `config/SCHEMAS.md` § 2.6 / § 2.7.

Regenerate after every skill add / move / rename. The `framework-navigator` skill consumes this for catalog browsing and description-based matching.

**Do not hand-edit.** Edit `SKILL.md` frontmatter, then regenerate.

## `skills.json` (generated)

Same data as `skills.csv` in JSON form, intended for programmatic consumers (the framework-navigator skill, validation tooling). Regenerated alongside `skills.csv` by the same script.

## `workflow-graph.yaml` (hand-authored)

Captures the parts of the framework's flow that *can't* be inferred from frontmatter:

- Stage groupings (which skills belong to which stage)
- Workflow edges (`before` / `after` between skills)
- Required gates (which reviews block which transitions)
- Mode-aware routing (greenfield / brownfield / quick-dev variants)

Edit when stage flow changes or new gates are added. The validation pass (migration task #8) checks that every workflow-graph reference resolves to a registry entry.

## Operating notes

### Regenerating the registry

```
python3 scripts/build-registry.py            # write skills.csv + skills.json
python3 scripts/build-registry.py --dry-run  # parse + validate, write nothing
python3 scripts/build-registry.py --verbose  # print one line per skill
```

The script depends only on the Python 3 standard library (no `pyyaml`).

### When to run

Run `build-registry.py` after any of:

- A new skill is added (new `SKILL.md`).
- A skill is moved between stages or renamed (folder rename).
- A skill's `SKILL.md` frontmatter is edited (especially `name` or `description`).
- The references/ trio is added or removed.

### When to edit `workflow-graph.yaml`

Edit `workflow-graph.yaml` directly (the script never touches it) when:

- Stage flow changes (a new stage is introduced, an existing stage is removed/reordered).
- A gate changes (a new review skill blocks a transition, an existing gate is dropped).
- A new flow is added (e.g. a fourth top-level mode beyond greenfield/brownfield/quick-dev).
- A new "anytime" cross-cutting utility is created.

Skill names referenced in this YAML must match the `name` field of an existing `SKILL.md`. Re-run `build-registry.py` first to confirm the registry view is current, then verify references by hand.

### Validation surface

`build-registry.py` warns (does not fail) on:

- Missing required frontmatter fields (`name`, `description`).
- Mismatch between `name` and the containing folder.
- Missing `references/OVERVIEW.md`, `references/INPUTS-OUTPUTS.md`, or `references/EXAMPLE.md`.
- `SKILL.md` longer than 200 lines.

The deeper cross-checks against `workflow-graph.yaml` (every flow / gate / anytime skill resolves to a registry entry; no orphan skills) live in the task #8 validation pass.
