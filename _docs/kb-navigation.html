A.I.D.E. · Knowledge base

How AIDE skills use the knowledge base

How the framework decides what kind of KB content it needs to answer a question, and how much of it to read.

Short answer: the KB has no retrieval engine. There are no embeddings, no vector database and no navigation code. Every decision is written as markdown instructions that the agent follows using read, grep and glob. The logic sits in four layers.

1

Structure for routing

build-knowledge-base produces a predictable shape: an index, routing metadata on every file, and a dependency graph.

2

Pick the files

navigate-knowledge-base scores, expands and caps the list of files to load. It never reads component bodies.

3

Choose read depth

Each calling skill decides how deep to read each file: frontmatter, selected sections, or the full body.

4

Trust & freshness

Commit stamps, drift gates and the update rule decide whether KB content can be trusted or has to be checked against source.

Layer 1 — What the KB looks like

Routing only works because the KB has a fixed shape. It has two halves.

HalfFileRole in routing
Code-grounded
(generated, never edited by hand)		 ARCHITECTURE.md Root index. § 0 points to the human-grounded half, § 1 is the summary, § 2 the repo map, § 3 the component catalog, § 4 the Capability Index, § 5 the dependency diagram, § 6 cross-cutting concerns.
components/<repo>/<id>.md One file per logical component, sized as the unit of selection. Frontmatter is the routing metadata: description ("Use when …"), triggers, paths, depends_on, data_entities, last_verified_against_commit. The body is the knowledge: Overview, Key Responsibilities, Change-Impact Summary, Recent Activity.
graph.json Nodes plus typed edges (calls, consumes, depends-on, derives-from) for working out how far a change reaches. consumed_by is computed when the file is read.
Human-grounded
(under shared/)		 solution-context/, ai-rules/, operations/ Mission, personas, constraints, ownership, coding rules, deployment and SLOs. Each file has a "Use when …" description and triggers:, so the same matching finds them.
cross-cutting/<concern>.md Auth, logging, errors, security, performance, versioning. Added to the list by keyword.

The Capability Index is the curated routing layer. The build skill groups components by their main verb phrase and merges synonyms (for example, "submit cart" becomes "place order"). Its job is to separate cases where one trigger word matches several things: "pay" matches both checkout and refunds.

NAVIGATE.md (formerly CLAUDE.md) is the first file an agent reads. It sets the read order and three rules: never read the whole KB (load at most 7 components by default), treat stale components as hints and check them against source, and never edit the KB by hand.

Layer 2 — Picking the files

navigate-knowledge-base takes a feature description, a seed component for impact analysis, or a list of file paths (--from-paths), and returns a ranked, capped list of file paths. Each path comes with a tier and a one-line reason. It reads ARCHITECTURE.md, greps frontmatter, walks graph.json one hop in both directions, adds cross-cutting and solution-context files, and stops there. See the full algorithm →

Callers choose what type of data comes back through flags:

  • --profile=test-suite returns test-suite components instead of application code.
  • --profile-subkind narrows a test-suite query, for example to fixtures or shared utilities only.
  • --depth=two-hop returns a wider set of affected components.
  • --include-solution-context and --include-cross-cutting control whether shared/ files are added.

Since 2.8.0, every framework skill that selects components calls the navigator rather than doing its own lookup. Validator Check Q warns when a stage skill reads components/ or the Capability Index without naming it.

Layer 3 — Read depth

The navigator decides which files. The calling skill decides how much of each to read. In practice there is a step-down ladder:

  1. 1
    A section of ARCHITECTURE.mdQuestions about the whole system; capture-solution-context's questioning steps.
  2. 2
    Frontmatter onlyAlways used for selection, and returned inline so the caller doesn't need a second read.
  3. 3
    Selected body sections / top N rowsThe quality stage's reuse check reads frontmatter plus top rows only; quick-dev orientation reads frontmatter plus § 3 Change-Impact Summary.
  4. 4
    Full component bodyRequirements and design discovery; execution reads the seed and primary components.
  5. 5
    Raw source codeOnly when the KB has nothing, is stale, or the detail needed is below the KB's level (planning's code conventions).

Layer 4 — Trust & freshness

The navigator reports each component's last_verified_against_commit but does not judge it. Callers that care run detect-knowledge-base-drift --mode=gate first, or a configured hook does it for them (AGENTS.md shows a kb-check hook that runs before navigate-knowledge-base). After work ships, update-knowledge-base brings the affected components back in sync.

KB lookups are context only. They never limit which files a plan may change. If the navigator errors or returns nothing, execution and quick-dev note it and carry on from the requirements, design or spec.

Knowledge-base stage · Selector

navigate-knowledge-base

The selector the whole framework uses at load time. It decides which files to load, never how much of each. It writes nothing, has no side effects, and can be called as often as needed.

Input
One of: a free-text feature description or trigger list, --seed-component-id for impact analysis, or --from-paths to find the components that own a set of files.
Reads
NAVIGATE.md (or CLAUDE.md in older KBs), ARCHITECTURE.md § 1–4, graph.json, and component frontmatter only via grep.
Returns
A ranked list. Each entry has path, tier, why, score, the parsed frontmatter, repo and last_verified_against_commit. With --from-paths, files no component owns come back as unmatched.
Never does
Read component bodies, check freshness, or write to the KB.

The algorithm

  1. Find the navigation file. NAVIGATE.md, falling back to CLAUDE.md.
  2. Read ARCHITECTURE.md § 1–4. Always done; about 5–15 KB.
  3. Look up capabilities. Split the description into words, reduce them to base forms, and score candidates against the Capability Index and each component's triggers and description. With --seed-component-id this is skipped. With --from-paths, each path is matched against component paths: globs and source_doc instead (same rules as update-knowledge-base step 01), and every hit enters the seed tier.
  4. Expand along the graph. One hop along depends_on (what the component calls) and consumed_by (what calls it). Both directions matter, because changing A affects A's callers. --depth=two-hop repeats this once more.
  5. Add cross-cutting concerns. If the description mentions auth, logging, errors, security, performance or versioning, add shared/cross-cutting/<concern>.md.
  6. Add solution context. Grep triggers: in shared/solution-context, ai-rules and operations.
  7. Rank and cap. With --include-stale=false, stale components are dropped first. Components (seed, primary, one-hop and two-hop tiers) are capped at 7 by default; cross-cutting and shared/ files don't count toward the cap.
  8. Return the list.

Scoring weights

SignalWeight
Exact phrase match on a Capability Index row1.0
Direct hit on --seed-component-id1.0 (seed tier)
--from-paths literal path match1.0 (seed tier)
--from-paths glob match0.9 (seed tier)
Capability row overlap of 2 or more words0.7
A trigger appears verbatim in the description0.6
One-hop graph neighbour of a primary match0.5
A trigger partly overlaps the description0.4
Cross-cutting keyword in the description0.4
Overlap with the "Use when …" description0.3
Two-hop graph neighbour (only with --depth=two-hop)0.25

A file is included if its score is at least 0.3. Ranking uses tier_rank × 1000 + score. Scores rank entries within a tier. Tier order: seed > primary > one-hop > two-hop > cross-cutting > solution-context > ai-rules > operations.

Flags that change what kind of data comes back

FlagEffect
--max-components (default 7)Hard cap on components. If it's lower than the number of primary matches, neighbours are dropped and only the top primaries are returned.
--from-pathsStarts from file paths instead of a description. Callers that want only the owning components keep the seed tier and drop the neighbours (as execute-increments step 06 does).
--include-stale=falseDrops components whose commit stamp is behind and whose paths overlap recent changes. Needs access to the source repos.
--depth=two-hopWider set of affected components. Only on explicit request, because it can grow past 20 components.
--profile=test-suiteDraws candidates only from kind: test-suite components and ranks them above application code. Graph expansion isn't filtered, so the application components under test still appear.
--profile-subkindNarrows to runner, shared-utilities, fixtures, marker-vocabulary, feature-inventory, environment-matrix, ci-surface or ownership.
--include-cross-cutting / --include-solution-contextTurn the shared/ tiers on or off. Both default to on.

Edge cases

  • No matches: returns an empty list, and the caller decides whether to fall back to ARCHITECTURE.md or the raw repos.
  • Empty test-suite profile: must say so explicitly. It must never quietly fall back to application components, which would give results that look right but are wrong.
  • Missing graph.json: warns and returns primary matches only.
  • KB not built (ARCHITECTURE.md missing): the navigator stops with an error. Callers in execution and quick-dev treat that as "no KB context" and continue.
  • Broad questions ("what does this system do?"): skip the navigator and read ARCHITECTURE.md § 1–4 directly.

Knowledge-base stage · Builder

build-knowledge-base

Doesn't answer questions itself. It produces the structure that makes routing possible, using the reverse-engineering Part A/B output.

When
When the KB is first set up, after reverse-engineering output exists.
Writes
components/, shared/cross-cutting/, graph.json, ARCHITECTURE.md, NAVIGATE.md and one NAVIGATE.md per repo.
Routing decisions it makes
How big a component is, which triggers it gets, what type each graph edge is, and how capabilities are grouped.

How each step affects routing

StepEffect on later lookups
03 — Emit componentsDefines the unit of selection: one file per feature or flow (not per endpoint or class), 5–30 per repo. Each gets a "Use when …" description, 5–10 triggers, paths, depends_on and a full commit SHA.
04 — Shared passFills in consumed_by and writes the cross-cutting files.
05 — Emit graphWorks out each edge's type from the component types (UI → API is calls, anything → framework is depends-on, and so on). Ambiguous edges default to depends-on and are flagged for review.
06 — Emit ARCHITECTURE.mdBuilds the Capability Index by grouping components by verb phrase and merging synonyms. Adds § 0 links to the human-grounded files, marked "pending" if those files don't exist yet.
07 — Emit NAVIGATE.mdWrites the read order and the selection, freshness and update rules that every later agent follows. Framework skills must call the navigator; only an agent without A.I.D.E. follows its full procedure by hand.

Because the Capability Index and graph.json are generated, editing them by hand is listed as a common mistake. Any change has to come from a rebuild or update-knowledge-base.

Knowledge-base stage · Writer

update-knowledge-base

The closing step of the execution flows. It brings the KB back in line with the shipped code, touching only the affected components. It never rebuilds the whole KB.

Called by
execute-increments (step 06) and execute-quick-change, after the user confirms the change.
Scope rule
Affected components are those whose paths: globs match the files changed in the feature's diff. Both modes use the same rule.
Full mode
Re-derives frontmatter and bodies, adds a change-tracker row, writes an ADR if a decision threshold was crossed, regenerates the changed parts of graph.json, and updates the Capability Index if any triggers changed.
--scope=catalog-only
Used by quick-dev. Updates only description, last_feature_id, last_verified_against_commit and the change tracker. Doesn't re-derive bodies or write ADRs.

Catalog-only mode doesn't re-check components whose paths: didn't match the diff, even if their commit stamp is stale. Spotting those is detect-knowledge-base-drift's job.

Knowledge-base stage · Trust

detect-knowledge-base-drift

The freshness check the navigator doesn't do. Callers that need to trust what they read run it first.

LayerCheck--mode=gate--mode=full
L1Commit stamp vs. repo HEAD✓✓
L2Structural diff✓✓
L3The model checks whether the doc still matches the code—✓
L4Full coverage sweep—✓

Gate mode fails on any L1 or L2 hit of medium severity or higher, so it suits PR pipelines. Each finding comes with a recommended action: update a feature, run a coverage delta, or rebuild if more than half the KB has drifted.

A kb-check hook (example in AGENTS.md) can run it automatically before navigate-knowledge-base.

Knowledge-base stage · Builder

capture-solution-context, generate-ai-rules, document-operations

These skills write the human-grounded half of the KB under shared/. The navigator adds these files as lower-ranked tiers alongside component matches.

Writes
shared/solution-context/ (six files: overview, personas, goals, constraints, integrations, ownership), shared/ai-rules/project-context.md, shared/operations/.
Reads while writing
Only sections of ARCHITECTURE.md: § 1 for domain context, § 2 for repo ownership, § 4 for linking personas and KPIs to components.
How they become findable
Every file carries description: Use when …, triggers: and optionally related_components. The navigator matches on that wording.

These files don't count toward the component cap. They're small, and the skill avoids letting supporting context push out a component the question actually needs. They're meant for project-wide questions about architecture, compliance or ownership, not single-component changes.

Delivery stage · Reader

create-requirements-package

Brownfield discovery queries the KB before reading source repos. The repos are the fallback when the KB has nothing.

When
Step 01 discovery, in brownfield or quick-dev flows, when project.paths.knowledge_base_path is set.
Query
navigate-knowledge-base with the change description (default profile, solution context included).
Read depth
Full component bodies for the primary and one-hop entries; cross-cutting and solution-context files where the change raises that concern.
Freshness
Compares last_verified_against_commit (returned by the navigator) against staleness_warning_days; stale components are flagged in existing-artifact-review.md.
Writes to KB
No.

How it works

  1. Call the navigator with the change description. It also returns the components that call the affected area, and any matching constraints, personas or ownership files.
  2. Read the returned entries in rank order. If nothing comes back, fall back to ARCHITECTURE.md § 1–4, then the source repos, and note the gap.
  3. Check staleness and flag anything out of date.
  4. Use the KB-informed picture to ask targeted questions, so the BA/PO doesn't have to explain the system from scratch.

Before 2.8.0 this step did its own Capability Index lookup and skipped the navigator's graph walk. It now calls the navigator, so the components that call the affected area are included.

Delivery stage · Indirect

create-implementation-package

Doesn't call the KB. It's grounded in the KB indirectly, through the approved Solution Design Package, and adds code-level detail by reading source.

Inputs
Solution Design Package (required; the skill stops if it isn't approved), architecture-baseline.md (if present), Requirements Package (required), codebase access, coding standards.
Scoping
The analysis scope comes from the design's component map and data flows, not from a KB query.
Read depth
Raw source code inside that scope, for conventions the KB doesn't record: DI, error handling, test naming, file locations.
Writes to KB
No.

Remaining gap: planning never checks the KB itself. If the KB changes between design and planning, or design discovery missed a component, planning won't notice. Delivery stage · Reader, then hands off to update

execute-increments

Looks up the components an increment touches before opening code, and after the increment ships, works back from the changed files to the components that need updating.

Read (step 01)
Calls navigate-knowledge-base, alongside reading the FRs and design sections.
Query
The KB component IDs the design cites for the increment, as --seed-component-id; otherwise the increment's Goal and Plan as the description.
Read depth
Seed and primary component bodies; one-hop entries for the integration points the Plan names. Stale components are treated as hints and checked against source.
Write (step 06)
Calls the navigator with --from-paths for every file the increment changed, keeps the seed tier as the affected components, reports unowned files, and hands off to update-knowledge-base.

Context only. The lookup never limits which files the Plan may change. If the navigator errors (for example, the KB isn't built yet) or returns nothing, step 01 notes it and continues, and step 06 skips the KB handoff. A KB problem is never a halt condition.

Delivery stage · Reader, then catalog-only update

quick-dev (plan-quick-change, execute-quick-change)

Looks up ownership and impact while planning, and refreshes only the catalog when the change is done.

Read
plan-quick-change orientation calls navigate-knowledge-base before opening source files: --from-paths with the spec's "Where" files, or the change summary when the spec names no files.
Read depth
Frontmatter and § 3 Change-Impact Summary only. Quick-dev needs ownership and blast radius, not a full component read.
Scope signal
If more than two one-hop components look like they need changes, the agent names them and asks the user whether to stay in quick-dev. The KB never triggers the escape hatch on its own.
Write
update-knowledge-base --scope=catalog-only, run only after the Completion Confirmation Gate clears.
Trade-off
The catalog reflects the change without a full re-derivation, so component bodies may lag until a full update or a drift sweep.

The gate is strict: a passing test suite or an open PR isn't confirmation. If the user stays silent or confirms only part of the change, the KB update is held back.

Gaps & inconsistencies

Places where the documented logic is less precise, or less consistent, than it looks.

1. The scoring is advisory, not run as code

The weights, the 0.3 threshold and the tier formula are written for the model to follow. Nothing calculates them exactly, so results are roughly consistent from run to run, not identical.

2. Planning only reaches the KB through the design

Planning is scoped by the design's component map and never checks the KB itself, so changes to the KB after design aren't picked up. This may be fine as designed.

3. Read depth isn't fully standardised

The quality skills, quick-dev, requirements and execution now say how deep to read. Design still leaves it to the model, and there's no shared vocabulary (frontmatter / sections / full) across skills.

Resolved in 2.8.0:

  • The navigator's docs agreed with each other only in part. SKILL.md now owns the tier order and cap rule; INPUTS-OUTPUTS.md documents every flag and tier. Validator Check P warns if a flag in SKILL.md is missing from the reference.
  • Not every caller went through the navigator. Requirements discovery, execute-increments, manage-bugs, quick-dev orientation and design C4 reuse now all call it. Validator Check Q warns on direct reads.
