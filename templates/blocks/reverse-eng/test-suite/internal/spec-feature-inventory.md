## 8. Spec / Feature Inventory

A flat, scannable index of every spec / feature file in the suite: what it covers, what tags it carries, what shared utilities and page objects it depends on, and which application increment IDs (INC-XXX) or acceptance-criteria IDs it maps back to. The reader should be able to answer "do we test X?" without grep'ing the repo.

Map each spec / scenario to its requirement-side ID. The mapping is the bridge that lets `audit-quality-coverage` run cleanly — without it, the audit cannot tell whether INC-042 is genuinely covered or whether the team just wrote a test that happens to mention "042".

**Orphans and near-duplicates (remediation queue):**

| File | Issue | Recommended action |
|---|---|---|
| `{{orphan-1}}` | Maps to no INC / FR / AC | Document mapping or delete |
| `{{dup-1}}` | Near-duplicate of `{{other-1}}` (90% scenario overlap) | Consolidate; one canonical, one deleted |

**Mapping conventions:**

- The mapping cell uses comma-separated IDs (`INC-042, FR-2.1, AC-2.1.3`).
- An empty mapping cell is treated as an orphan by `audit-quality-coverage` and surfaces as a finding.
- When a spec covers multiple ACs, ALL must be listed; partial mappings produce false-positive coverage signals.
- When an AC is split across multiple specs, every spec is listed under the AC's row in the design package's traceability matrix — not just the "primary" one.
