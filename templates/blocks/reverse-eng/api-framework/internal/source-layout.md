## 2. Source Layout

A precise map of the source tree, package boundaries, and where each subsystem lives. The point is to short-circuit the discovery phase for a new maintainer or AI assistant — they should be able to ask "where does request parsing live?" and find the file in seconds. Verify the layout against the live repo with `tree -L 3` (or equivalent) and a grep for major export sites.

State the boundary rules explicitly: which modules may import which, and where one-way fences exist (e.g., core never imports from plugins). These rules are usually enforced via lint rules, package boundaries, or visibility modifiers; document where the enforcement lives so it's not silently broken in PRs.

**Boundary rules:**

- `core` MUST NOT import from `plugins/*` — plugins register into core, not the reverse.
- `plugins/*` MUST NOT import from each other — communicate via the plugin bus / events.
- `testing` may peek at `core` internals via a dedicated `__test__` export site.
- `cli` is the only package allowed to read from disk at module-load time.

**Module conventions:**

- Each subsystem has a single `index.ts` (or `mod.go`, `__init__.py`, etc.) that defines the public surface.
- Internal-only utilities live under `_internal/` and are not re-exported.
